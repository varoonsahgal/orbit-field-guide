The three faults at a glance#

Someone "migrated" the identity layer and left the chat app with a key that can't open anything, a blank settings card, and two bouncers who have never heard of the new key. Everything else in the platform is healthy.

# Where it's planted What's wrong The clue that gives it away The fix
1 Cognito → the class user pool → App clients The only app client for your lab id is orbit-student07-am01-web-client-legacy: a public web client with no client secret and no client_credentials grant The client's page has no Client secret row, and OAuth grant types doesn't list Client credentials Create a machine-to-machine app client with both supplychain scopes
2 Lambda → orbit-student07-am01-chat-handler → Environment variables ORCHESTRATOR_RUNTIME_ARN, COGNITO_DOMAIN, COGNITO_CLIENT_ID, COGNITO_CLIENT_SECRET, COGNITO_USER_POOL_ID are all empty strings The health page lists all five as MISSING and token says missing environment configuration Fill in the five values from your mission card and the new app client
3 Both JWT authorizers: the Gateway's Inbound Auth and the Runtime's inbound authorizer allowedClients contains only the legacy client id the orchestrator runtime rejected the token (HTTP 401/403), then Gateway rejected our token in warnings Add the new client id to both allowed-client lists
Important

The faults are chained: you can't see fault 3 until fault 2 is fixed, and fault 2 can't be fixed usefully until fault 1 is. That's why the handout says do the goals in order. In every example below, replace student07 with your lab id.

How the chain is supposed to work#

Three ideas carry the whole mission:

  • A confidential client has a secret; a public client doesn't. Cognito will only hand a token to software logging in as itself (client_credentials) if the app client has a secret. The legacy client was created as a browser-style public client, so it can never mint this kind of token.
  • The chat app reads its settings from environment variables at cold start. Five of them are blank. The health page is literally os.environ.get(...) printed as set/MISSING, followed by one live attempt to get a token.
  • Every JWT authorizer keeps its own guest list. The Runtime checks allowedClients; the agent then passes the same token to the Gateway, which checks its own allowedClients. A client that's on one list and not the other produces a different error for each.

01Phase 110 minutesReading the evidence#

Before changing anything, here is what each observation from the handout's Phase 1 tells you.

The chat error#

The chat handler never got as far as calling the agent. The error is raised inside its own get_token() because three of the variables it needs are empty. No trace, no pills confirms the request died inside the Lambda.

The health page#

Open <chat URL>health. Broken, it reads:

JSON
{
  "student": "student07",
  "module": "am01",
  "region": "us-west-2",
  "config": {
    "ORCHESTRATOR_RUNTIME_ARN": "MISSING",
    "COGNITO_DOMAIN": "MISSING",
    "COGNITO_CLIENT_ID": "MISSING",
    "COGNITO_CLIENT_SECRET": "MISSING",
    "COGNITO_USER_POOL_ID": "MISSING"
  },
  "token": "Authentication service unavailable: missing environment configuration: COGNITO_DOMAIN, COGNITO_CLIENT_ID, COGNITO_CLIENT_SECRET"
}

Two things to notice. First, config only tells you whether a value is present, not whether it's right: a wrong value still shows set. Second, the token line is a live test: every time you reload the page, the Lambda tries to get a token with whatever is configured right now, so it's your fastest feedback loop for Goals 1 and 2.

The legacy app client#

Amazon Cognito → User pools → the class pool (named on your mission card) → App clients → orbit-student07-am01-web-client-legacy.

What you look at What you see Why it matters
Client secret row Not there at all (or "–") No secret = Cognito cannot authenticate this client for client_credentials
Authentication flows ALLOW_USER_SRP_AUTH, ALLOW_REFRESH_TOKEN_AUTH These are human sign-in flows. There's no machine flow here
Login pages tab → OAuth 2.0 grant types Nothing selected, or no custom scopes Even with a secret it couldn't ask for supplychain/read

Predict first the handout asks whether filling in the settings alone would fix the chat. Answer: no. Which client id would you even paste? The legacy one has no secret, so COGNITO_CLIENT_SECRET has nothing to hold, and Cognito would answer invalid_client (or unauthorized_client) to the token request. Fault 1 has to go first.

The two guest lists#

  • Bedrock AgentCore → Gateways → orbit-student07-am01-gateway → Inbound Auth (sometimes labelled Inbound authorization): Allowed clients shows exactly one id. It's the legacy client's id (compare with legacy_client_ids on your card).
  • Bedrock AgentCore → Runtime → orbit_student07_am01_orchestrator → the inbound identity / authorizer section: the same single legacy id.

Both discovery URLs are correct and identical. Write the legacy id down: you'll keep it in both lists (removing it isn't required and avoids a needless runtime redeploy) and add a second id next to it.

02Phase 225 minutesThe fix, click by click#

Goal1Create the machine-to-machine app client#

Expected: a new app client whose page shows a Client secret, the Client credentials grant and both supplychain custom scopes.

  1. Amazon Cognito → User pools → open the class pool named on your mission card. Check the Region selector says us-west-2 first.
  2. In the left menu choose Applications → App clients, then Create app client.
  3. Under Application type, choose Machine-to-machine application. This is the choice that matters: it tells Cognito to generate a client secret and enable the client_credentials grant.
  4. Name: orbit-student07-am01-m2m (any name works, but it must contain your lab id so you and your classmates can tell the clients apart).
  5. If the form shows a Custom scopes picker for the supplychain resource server, tick supplychain/read and supplychain/write now. If it doesn't, continue; you'll add them in step 7.
  6. Choose Create app client. You land on the new client's page.
  7. Open the Login pages tab. Under Managed login pages configuration (or Hosted UI) choose Edit. In OAuth 2.0 grant types make sure Client credentials is selected. In Custom scopes, select supplychain/read and supplychain/write. Save changes.
  8. Back on the App client information panel, copy two values into a scratch note:
    • Client ID (26 lowercase characters)
    • Client secret → Show client secret, then copy (about 50 characters)
Warning

Don't create a new resource server or new scopes. supplychain with read and write already exists on the pool; you're only allowing the existing scopes on your new client.

CloudShell alternative for Goal 1

Open CloudShell (the >_ icon) and run, with your pool id from the mission card:

Shell
POOL=us-west-2_EXAMPLE      # cognito_user_pool_id from your card
ME=student07                # your lab id

aws cognito-idp create-user-pool-client \
  --user-pool-id "$POOL" \
  --client-name "orbit-$ME-am01-m2m" \
  --generate-secret \
  --allowed-o-auth-flows-user-pool-client \
  --allowed-o-auth-flows client_credentials \
  --allowed-o-auth-scopes supplychain/read supplychain/write \
  --supported-identity-providers COGNITO \
  --query 'UserPoolClient.{ClientId:ClientId,ClientSecret:ClientSecret,Flows:AllowedOAuthFlows,Scopes:AllowedOAuthScopes}'

The output shows the id, the secret, ["client_credentials"] and both scopes in one go.

  • The new client page shows a client secret, the client credentials grant, and both custom scopes.

Goal2Fill in the chat app's five settings#

Expected: the health page shows every setting as set and token: ok.

  1. Lambda → Functions → orbit-student07-am01-chat-handler (filter the list by your lab id).
  2. Configuration tab → Environment variables → Edit.
  3. You'll see seven keys. Leave STUDENT_ID and MODULE as they are and fill the five empty ones exactly as below:
Key Paste Shape check
ORCHESTRATOR_RUNTIME_ARN orchestrator_runtime_arns from your mission card starts arn:aws:bedrock-agentcore:us-west-2:…:runtime/orbit_student07_am01_orchestrator-…
COGNITO_DOMAIN cognito_domain from your card a host name ending in .amazoncognito.com; no https://, no trailing / or path
COGNITO_CLIENT_ID the new client id from Goal 1 26 lowercase letters/digits
COGNITO_CLIENT_SECRET the new client secret from Goal 1 ~50 characters, mixed case
COGNITO_USER_POOL_ID cognito_user_pool_id from your card starts with us-west-2_
  1. Save. Lambda replaces its containers, so the new values apply within a few seconds.
  2. Reload <chat URL>health:
JSON
{
  "config": {
    "ORCHESTRATOR_RUNTIME_ARN": "set",
    "COGNITO_DOMAIN": "set",
    "COGNITO_CLIENT_ID": "set",
    "COGNITO_CLIENT_SECRET": "set",
    "COGNITO_USER_POOL_ID": "set"
  },
  "cognito_discovery": { "url": "https://cognito-idp.us-west-2.amazonaws.com/us-west-2_EXAMPLE/.well-known/openid-configuration", "http_status": 200 },
  "token": "ok"
}

token: ok means Cognito accepted your client id + secret and the two scopes. If instead you see:

token says Cause Fix
Cognito token endpoint returned 400: {"error":"invalid_client"} wrong client id or secret, or you pasted the legacy id Re-copy both values from the new client
… returned 400: {"error":"invalid_scope"} the client isn't allowed one of the scopes Goal 1 step 7
… returned 400: {"error":"unauthorized_client"} client_credentials isn't enabled on the client Goal 1 step 7
could not reach Cognito token endpoint https://https://… or …/oauth2/token: [Errno -2] COGNITO_DOMAIN has a scheme, a path or a typo Paste the bare host name
cognito_discovery.http_status is 400/404 COGNITO_USER_POOL_ID is wrong Copy the pool id again (it starts us-west-2_)
CloudShell alternative for Goal 2
Shell
FN=orbit-student07-am01-chat-handler
aws lambda update-function-configuration --function-name "$FN" --environment "Variables={
  STUDENT_ID=student07,MODULE=am01,
  ORCHESTRATOR_RUNTIME_ARN=<runtime arn>,
  COGNITO_DOMAIN=<cognito_domain>,
  COGNITO_CLIENT_ID=<new client id>,
  COGNITO_CLIENT_SECRET=<new client secret>,
  COGNITO_USER_POOL_ID=<pool id>}" --query 'Environment.Variables' 
curl -s "<chat url>health" | jq .

update-function-configuration replaces the whole variable map, which is why STUDENT_ID and MODULE are repeated.

  • Health page: all five set, token: ok.

Now send the test message again. The error changes, which is progress:

The chat app now has a valid token; bouncer 1 (the Runtime) looked at its client_id claim and didn't find it on the guest list. That's fault 3.

Goal3Put the new client on both guest lists#

Expected: a normal reply; trace shows token_source: "inbound" and warnings: []; the gateway pill is green with 9 tools.

Do the Gateway first (it updates in seconds), then the Runtime (which starts a new version and takes about a minute).

3a · The Gateway (bouncer 2)

  1. Bedrock AgentCore → Gateways → orbit-student07-am01-gateway.
  2. Find the Inbound Auth section and choose Edit.
  3. Leave Discovery URL exactly as it is. Under Allowed clients, choose Add and paste your new client id. Keep the legacy id in the list.
  4. Save. The gateway status briefly shows UPDATING, then READY.

3b · The Runtime (bouncer 1)

  1. Bedrock AgentCore → Runtime → orbit_student07_am01_orchestrator.
  2. Choose Edit (top right of the runtime page).
  3. Scroll to the Inbound identity / Authorizer configuration section (the one that shows the discovery URL and the legacy client id). Add your new client id to Allowed clients. Change nothing else on the form: the code location, role, network mode and environment variables must stay as they are.
  4. Save / Update runtime. The status changes from READY to UPDATING while AgentCore builds a new version (v2). The old version keeps answering, and rejecting, until the new one is live, so wait until the status is READY again before testing.
CloudShell alternative for Goal 3

Both update calls require the full current configuration, so read it first and only change allowedClients:

Shell
GW=orbit-student07-am01-gateway-xxxxxxxxxx         # gateway_ids from your card
RT=orbit_student07_am01_orchestrator-xxxxxxxxxx    # orchestrator_runtime_ids from your card
NEW=<new client id>

# Gateway
aws bedrock-agentcore-control get-gateway --gateway-identifier "$GW" > gw.json
jq --arg c "$NEW" '{gatewayIdentifier:.gatewayId,name,roleArn,protocolType,protocolConfiguration,authorizerType,
  authorizerConfiguration:(.authorizerConfiguration|.customJWTAuthorizer.allowedClients += [$c])}' gw.json > gw-update.json
aws bedrock-agentcore-control update-gateway --cli-input-json file://gw-update.json --query status

# Runtime
aws bedrock-agentcore-control get-agent-runtime --agent-runtime-id "$RT" > rt.json
jq --arg c "$NEW" '{agentRuntimeId,agentRuntimeArtifact,roleArn,networkConfiguration,protocolConfiguration,
  environmentVariables,requestHeaderConfiguration,
  authorizerConfiguration:(.authorizerConfiguration|.customJWTAuthorizer.allowedClients += [$c])}' rt.json > rt-update.json
aws bedrock-agentcore-control update-agent-runtime --cli-input-json file://rt-update.json --query '{status:status,version:agentRuntimeVersion}'

Then poll aws bedrock-agentcore-control get-agent-runtime --agent-runtime-id "$RT" --query status until it prints READY.

If you fix the Runtime but not the Gateway, you get a reply, but it's a hollow one:

The pill is green because GATEWAY_URL is configured, but 0 tools and the warning say bouncer 2 turned the token away. The handout's "green isn't proof" rule in action.

  • Both the Gateway and the Runtime list the new client id, and the runtime is READY.

03Phase 35 minutesFlight test and how to read the trace#

Expand trace under the reply. The fields that prove the chain:

JSON
{
  "token_source": "inbound",
  "gateway_configured": true,
  "tools_discovered": 9,
  "tools_called": [],
  "warnings": []
}
  • token_source: "inbound": the agent used the token the chat app sent (passed through by the Runtime's Authorization header allow-list), not one it minted itself.
  • tools_discovered: 9: the Gateway accepted that same token and answered tools/list with 3 inventory + 2 supplier + 2 logistics + 2 quality tools.
  • warnings: []: nothing failed on the way.

Second test:

tools_called[0].tool is inventory-target___get_stock_summary: target name, three underscores, tool name. The Gateway invoked your orbit-student07-am01-inventory Lambda using its own IAM role and relayed the result.

What you just proved: one token, minted by your new confidential client, passed two independent JWT authorizers, and the agent used it to discover and call tools.

  • Both flight tests pass with the traces above.

If it still fails#

Symptom Where the chain broke Check
Health shows MISSING Lambda env vars Did you Save the environment variables? Are you looking at your function?
token says invalid_client Cognito Client id/secret mismatch, or the legacy id was pasted. Secrets copied from a PDF often lose characters: re-copy from the console
token: ok, chat says runtime rejected the token (HTTP 403) Runtime authorizer New id not in the Runtime's allowed clients, or the runtime is still UPDATING
Reply arrives, warnings has Gateway rejected our token (401), 0 tools Gateway authorizer New id not in the Gateway's allowed clients
warnings has Gateway rejected our token (403) Gateway authorizer Same as above; 403 appears when the token is valid but the client isn't allowed
HTTP 424 / Flight controller fault Agent code Not a planted fault. Usually the runtime is mid-update; wait and retry. If it persists, ask the instructor to check the runtime logs
Everything green but 7 tools Gateway targets A target is missing: that's Mission B's territory. Mission A environments always have 4 targets

Think about it: the answers#

  1. Why does the chat app get the token on the server instead of letting the browser ask Cognito? Because the client_credentials grant needs the client secret, and anything sent to a browser is public. A browser would use a user-facing flow (authorization code + PKCE) and a human would sign in. Here the chat app is the client, so it keeps the secret in its environment and mints the token server-side.
  2. If you had fixed only the Gateway's guest list, where would the chain break? At bouncer 1. The chat app would still get the orchestrator runtime rejected the token (HTTP 403) and no trace at all, because the request never reaches the agent, so the agent never calls the Gateway. Fixing the "second" bouncer first produces no visible change: a classic trap.
  3. The chat URL has no login of its own. Why is that risky? Anyone with the URL can spend your account's Bedrock and AgentCore budget and read your tool data. In a product you'd put the Function URL behind AWS_IAM auth, API Gateway with a Cognito authorizer, or CloudFront + WAF, and the user would sign in with their own Cognito identity so each token carries a real user rather than one shared machine identity.

Key takeaways#

  • Machine-to-machine = confidential client. No secret, no client_credentials. Cognito's Machine-to-machine application type sets up both.
  • Scopes are granted per client. A token can only carry scopes its client was allowed; the chat app asks for both supplychain scopes every time.
  • Each JWT authorizer has its own allowedClients. The Runtime and the Gateway each check the same token independently. Update both, and read the error to learn which one is still saying no.
  • Configuration is part of the security chain. The health page's live token test is the quickest way to separate "wrong settings" from "wrong identity".
  • Runtime edits create a version. Nothing you change on an AgentCore Runtime takes effect until the status is back to READY.
