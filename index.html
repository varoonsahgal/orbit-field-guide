The shared-account rules

Read before Mission 01

Up to thirty people share one AWS training account, so names keep you apart and a few rules keep you safe.

  1. Region: everything lives in US West (Oregon), us-west-2. The console remembers a Region per service, so glance at the selector every time you open a new one.
  2. Your MY_ID: your seat number plus two random digits, lowercase, for example s07x42. Choose it once and use it in every name in every mission.
  3. Read-only shared resources: anything starting orbit-academy- (the mystery role, the Cognito pool, the OpenSearch domain) belongs to the instructor. Look, never edit.
  4. Never open Edit or Delete on anything without your MY_ID. The IAM console lists hundreds of roles from other courses; filter before you click.
Trap · the service-specific naming rules

The same MY_ID appears with hyphens in most names and with underscores in harness names: orbit-s07x42-gateway but orbit_s07x42_agent. Harnesses accept only letters, digits and _; gateways and targets accept only letters, digits and -. Copy the names from the crib sheet.

Management plane vs data plane

A distinction that saves hours

Creating a resource and using a resource are checked against different identities.

When you click Create gateway, IAM checks your console identity (the management plane). When the harness later lists that gateway's tools, IAM checks the harness execution role (the data plane). You being an administrator says nothing about what your agent may do at run time, which is exactly why the agent hits a 403 in Mission 04 even though you created everything yourself.

Tidbit · iam:PassRole

The one place the two planes touch: when you tell Lambda or AgentCore “run as role X”, you need iam:PassRole on X. Without it, any recruit could hand a powerful role to a function and borrow its permissions.

Reading failures

Every mission plants at least one error. The skill is not avoiding them; it is reading them: which layer refused, which identity was refused, and which of the three kinds of “no” you got.

The three kinds of “no”

IAM evaluation

Every IAM denial is one of three things, and each one has a different fix.

KindWhat happenedTypical messageFix
Implicit denyNo statement allowed the action on that resourcebecause no identity-based policy allows the … actionAdd a narrow Allow on the right principal
Explicit denyA statement says "Effect": "Deny"; it beats every Allowwith an explicit deny in …Change or scope the Deny; adding Allows never works
Trust failureThe service may not even become the rolenot authorized to perform AssumeRoleFix the role's trust policy (or wait out propagation)

The layer ladder

Where did it die?

An agent request climbs these rungs in order. Find the lowest rung that failed; everything above it is irrelevant until that one is fixed.

LayerSymptomWhose permission
1Inbound403 Missing Authentication Token, OAuth authorization failedThe caller: IAM identity or the JWT's issuer, client, scope
2Tool loadingFailed to load tool … 403 Forbidden from a /mcp URLHarness role needs bedrock-agentcore:InvokeGateway
3ModelAccessDeniedException … bedrock:InvokeModel, ValidationException, invalid sequence as part of ToolUseThe role running the code; model access; model choice
4Tool executionLambda error in the trace, or a gateway target that failsGateway role (invoke the Lambda), then the Lambda's own role
5Business logicAgent “succeeds” but claims something untrueNo IAM fix: tool design, system prompt, evidence
Analogy · the spaceport

Rung 1 is the gate guard checking your badge. Rung 2 is the agent being allowed into the tool hangar. Rung 3 is the radio to mission control. Rung 4 is the hangar crew actually moving the part. Rung 5 is whether what the pilot says happened matches what did.

Status codes you will read

HTTP
CodeMeaning in these labs
200Accepted and answered. Still check the content (rung 5).
400The request itself was malformed: invalid_client, invalid_scope, invalid_grant at the Cognito token endpoint.
401 / 403Refused. MissingAuthenticationToken = unsigned or no token. AccessDenied = signed, identified, not allowed.

Trap · retrying instantly

IAM is eventually consistent. A policy you just saved can take a few seconds to apply everywhere, and a role a wizard just created can be invisible for longer. Wait 10–60 seconds before deciding a fix did not work, and in AgentCore start a new session so tools are reloaded.

A four-step method

Use it every time
  1. Read the whole message. Expand Details or Show full error. The principal, action and resource are almost always in it.
  2. Name the rung on the ladder and the principal that was refused.
  3. Make the smallest change on that principal: one action, one resource ARN.
  4. Prove it with evidence: a green test, a trace step, a REPORT line, a 200 alongside a 403.

Account → Region → Availability Zone

Three boxes

An account is the billing and security boundary; a Region is a geographic cluster of data centres with its own copy of most services; an Availability Zone is a fault boundary inside a Region.

Resources in one Region are invisible from another: a knowledge base in Oregon cannot be attached to an agent in Virginia. A few services are global (IAM, Route 53, CloudFront), and the Region selector reads Global while you are in them. That is why the IAM role you build today works everywhere, while your Lambda function will exist only in Oregon.

Tidbit · zone names are shuffled

Every account sees its own mapping from zone names (us-west-2a) to zone IDs (usw2-az1), so customers spread load evenly. Your us-west-2a and another account's can be different buildings. When two accounts must line up, compare zone IDs.

Try it · the console in five clicks
  • Option+S / Alt+S jumps to the search box; you search the console, you never browse it.
  • Star IAM, Lambda, CloudWatch, Amazon Bedrock and Amazon Bedrock AgentCore to pin them to the favourites bar.
  • The account menu shows the account ID and your sign-in name. Write both in your ledger.

IAM: principals and policies

Identity and Access Management

IAM answers one question for every API call: is this principal allowed to perform this action on this resource right now?

  • Principals make requests: IAM users (people or scripts with long-term credentials), roles (identities assumed for a short time by a person, a service, or another account) and groups (bags of users that share policies).
  • Identity-based policies attach to a user, group or role and need no Principal: the principal is whoever wears them.
  • Resource-based policies attach to the resource itself (a bucket, a secret, an OpenSearch domain) and must name a Principal, because the policy has to say who.
Analogy · user vs role

A user is an employee badge with your photo on it, valid until revoked. A role is a visitor pass from the front desk: whoever is allowed to pick it up wears it for an hour, then it expires. Services like Lambda and AgentCore only ever wear visitor passes.

The evaluation rule

Memorise this

Start from deny. An Allow opens the door. An explicit Deny slams it, every time.

Trust policy vs permissions policy

Every role has both

The trust policy says who may become the role; the permissions policy says what the role may do once assumed.

A role with trust but no permissions can be assumed and then do nothing. A role with permissions but the wrong trust can never be assumed by the service that needs it. In Phase 5 you build orbit-MY_ID-lambda-role: trusted by lambda.amazonaws.com, allowed only AWSLambdaBasicExecutionRole (three logs: actions).

Reading an ARN

Amazon Resource Name

An ARN reads as partition : service : Region : account : resource, and the empty fields tell you something.

arn:aws:iam: :111122223333:role/orbit-academy/orbit-academy-mystery-role
arn:aws:bedrock:us-west-2: :foundation-model/amazon.nova-lite-v1:0

IAM ARNs have an empty Region because IAM is global. Foundation-model ARNs have an empty account because AWS owns the models. The /orbit-academy/ in the first ARN is an IAM path, a folder-like prefix for organising roles.

Tidbit · this guide's account number

111122223333 is AWS's documentation placeholder. Your instructor gives you the real training account ID; copy real ARNs from the console rather than typing them.

The mystery role

IAM puzzle · Phase 4

The instructor planted orbit-academy-mystery-role, shaped like an AgentCore execution role. You answer ten questions about it from its trust and permissions tabs, then prove two of them in the IAM policy simulator or with aws iam simulate-principal-policy in CloudShell.

Debrief · three different “no” answers
  • Nova Pro is an implicit deny: nobody mentioned it.
  • The production secret is an explicit deny: a statement forbids it, and no Allow can override that.
  • Lambda cannot use the role at all: the trust policy never lets it in, so permissions never enter the picture.

When an agent fails with AccessDenied later in the course, your first question is always: which of the three is this?

Trap · fixing an explicit deny with an Allow

Challenge A asks whether adding Allow secretsmanager:GetSecretValue on orbit/prod/* would let the role read production secrets. It would not: the existing Deny still matches and Deny always wins. The smallest working change edits or narrows the Deny itself.

Tidbit · the confused deputy guard

The mystery role's trust policy adds aws:SourceAccount and aws:SourceArn conditions. They stop some other account's AgentCore resource from tricking the service into assuming your role on its behalf: the classic confused deputy problem.

CloudShell and signed requests

Phase 6

AWS CloudShell is a free browser shell (Amazon Linux, AWS CLI, Python) that runs in a Region with your console credentials already injected.

Every console click, CLI command and SDK call becomes an HTTPS request signed with Signature Version 4: a hash of the request, the date, the Region and the service, signed with your secret key. AWS recomputes the signature on its side. The secret itself never crosses the wire.

Try it · see the signature (CloudShell) 
# 1. Unsigned: AWS refuses it
curl -s 'https://sts.us-west-2.amazonaws.com/?Action=GetCallerIdentity&Version=2011-06-15'

# 2. Export the shell's temporary credentials
eval $(aws configure export-credentials --format env)

# 3. Signed with SigV4: AWS answers with your ARN
curl -s --aws-sigv4 aws:amz:us-west-2:sts \
  --user "$AWS_ACCESS_KEY_ID:$AWS_SECRET_ACCESS_KEY" \
  -H "x-amz-security-token: $AWS_SESSION_TOKEN" \
  'https://sts.us-west-2.amazonaws.com/?Action=GetCallerIdentity&Version=2011-06-15'
Trap · the CloudShell quota

Only 10 concurrent CloudShell sessions per account per Region. If yours refuses to start, you are the eleventh: close your tab when done, follow the instructor's waves, or use the console equivalent (every CloudShell step has one).

Check yourself · Mission 01
Why can an IAM role you create in Oregon be used by a function in Virginia, but the function itself cannot be seen from Virginia?

IAM is a global service with one namespace per account; Lambda is regional, so each function exists in exactly one Region.

What is the difference between MissingAuthenticationToken and AccessDenied?

The first means the request was not signed, so AWS does not know who you are. The second means AWS knows exactly who you are, evaluated your policies, and said no.

A role has AdministratorAccess and one statement that denies secretsmanager:* on orbit/prod/*. Can it read orbit/prod/api-key?

No. An explicit Deny beats every Allow, including AdministratorAccess.

Why does creating a Lambda function need permissions on IAM as well as on Lambda?

You hand the function an execution role, which requires iam:PassRole on that role. Otherwise anyone who can create functions could borrow any role's permissions.

Why does aws sts get-caller-identity work in CloudShell without configuring keys?

CloudShell injects temporary credentials for your console identity, so every CLI call is signed as you.

AWS Lambda in six terms

Code + config + role

A Lambda function is your code plus its configuration, run on demand and billed per request and per millisecond.

TermMeaning
Handlerlambda_function.lambda_handler(event, context). event is the JSON input; context is facts about this run (request ID, time left, memory).

Edit, then Deploy, then Test. Skip Deploy and Test runs whatever was there before, and you will chase a bug that is already fixed.

CloudWatch: where telemetry lands

Logs · metrics · Insights

Log group (one per function, /aws/lambda/<name>) → log streams (one per execution environment) → log events (every line you print, plus Lambda's own START, END and REPORT).

Metrics (Invocations, Duration, Errors, Throttles) appear on the function's Monitor tab without any code. The REPORT line is the raw material for every Lambda cost and performance question:

Try it · Logs Insights (CloudWatch → Logs → Log Analytics) 
filter @type = "REPORT"
| stats count() as invocations, avg(@duration) as avg_ms,

Tidbit · why two tests share one stream

A log stream belongs to one execution environment. Two quick tests reuse the same warm environment, so they land in the same stream, and only the first shows Init Duration.

The wall: reading AccessDenied

Phase 4

Your function calls Amazon Nova Lite with the Converse API. Its role allows logging and nothing else. It fails, and the message tells you exactly how to fix it.

An error occurred (AccessDeniedException) when calling the Converse operation:
User: arn:aws:sts::111122223333:assumed-role/orbit-MY_ID-lambda-role/orbit-MY_ID-hello
is not authorized to perform: bedrock:InvokeModel
on resource: arn:aws:bedrock:us-west-2::foundation-model/amazon.nova-lite-v1:0

  2. 2What: one action, bedrock:InvokeModel.
  3. 3On what: one model ARN.
  4. 4Why: implicit deny. So the fix is an Allow, on that role, for that action, on that ARN.
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "InvokeNovaLiteOnly",
    "Effect": "Allow",
    "Action": "bedrock:InvokeModel",

Add it as an inline policy named orbit-MY_ID-bedrock-invoke on orbit-MY_ID-lambda-role. Wait ten seconds, test again.

Debrief · least privilege, demonstrated

You never gave yourself permission to call Bedrock, and you never wrote "Resource": "*". Change MODEL_ID to amazon.nova-pro-v1:0 and the same error returns, which is exactly what least privilege is supposed to do.

The two gates on a model call

Bedrock

A model call passes model access (account level, set by an administrator) and then IAM (role level, set by you). No policy can bypass the first gate.

  • Model catalog: every model in the Region with its model ID (amazon.nova-lite-v1:0), modalities, context window and pricing.
  • Converse API: one request shape for every chat model: system, messages, inferenceConfig.
  • Tokens: the unit of billing. Every response reports inputTokens and outputTokens.
Trap · inference profiles need two ARNs

Some models are reached through a cross-Region inference profile such as us.amazon.nova-micro-v1:0, which routes to several Regions. The policy must allow the profile ARN and the foundation-model ARN in every Region it routes to (arn:aws:bedrock:*::foundation-model/amazon.nova-micro-v1:0). That is why the mystery role uses * for the Region on one model ARN.

Why the agent's role is not the tool's role

If the agent and its tools shared one role, a prompt-injected agent could do anything any tool can do. Separate roles mean the agent can only ask a gateway, and only the gateway can invoke the tool.

Cognito: who issues the tokens

Phase 7 · read-only

A Cognito user pool is a user directory plus an OAuth 2.0 / OpenID Connect server. AgentCore does not know your users; it trusts tokens the pool signs.

Public by designSecret, always
Issuer URL, discovery document (/.well-known/openid-configuration), JWKS public keys, hosted login page, a client IDPasswords, the pool's private signing keys, a confidential client's client secret, the tokens themselves

Signing in as your recruitNN user ends at https://localhost:8080/callback?code=… with This site can't be reached. That is expected: nothing listens on your laptop. The code in the address bar is a one-time authorization code a real app would exchange for tokens within five minutes.

Tidbit · why a public client is still safe

A public app client has no secret, but it can only send users to the hosted login page and back to its registered callback URLs. Without the user's password nobody gets a token, and the code is useless at any other redirect URI.

OpenSearch: the store with the lid off

Phase 8 · read-only

A domain is a managed OpenSearch cluster. It holds indexes of JSON documents; a mapping can declare a knn_vector field for embeddings.

Retrieval-augmented agents embed the question, run a k-NN search for the nearest vectors, and hand the matching documents to the model. Managed knowledge bases (Mission 03) do all of this for you; orbit-academy-search shows you what is underneath, with an index orbit-policies and an 8-dimensional embedding field (real ones have 256–1,536).

Tidbit · green with one node

A single-node domain is green only if every index has zero replicas. A replica must live on a different node from its primary, so with one node it has nowhere to go and the cluster turns yellow.

Trap · reading the domain's access policy

The domain has a resource-based policy: the instructor gets es:*, everyone else es:ESHttpGet and es:ESHttpHead. A signed PUT from CloudShell returns 403. That is correct, not broken.

Check yourself · Mission 02
Why did the IAM fix go on the role and not on your user?

The running code signs its Bedrock call with the execution role's temporary credentials. Your user is not part of that request at all.

What is the difference between Duration and Billed Duration?

Duration is how long your code ran; Billed Duration is that time rounded up to the next millisecond, which is what you pay for.

Your policy is correct but the test still fails ten seconds later. What do you check?

That the policy is on the role (not your user), that the resource ARN is exactly the Nova Lite ARN in us-west-2, and that you waited for propagation. Then test again.

Why is an environment variable the right place for a model ID and the wrong place for a client secret?

Environment variables are configuration, visible to anyone who can read the function's settings. A secret belongs in Secrets Manager, read at run time under a narrow IAM permission (Mission 05).

Why does a resource-based policy need a Principal and an identity-based one does not?

An identity-based policy applies to whoever it is attached to. A resource-based policy sits on the resource and must say which principals it is granting access to.

What a foundation model actually knows

Phase 1 · Playground

A foundation model predicts the most likely continuation of your prompt. It knows language patterns, not ORBIT's private, current return policy.

An inference is one call: prompt in, text out, billed in tokens (roughly ¾ of an English word). A hallucination is a fluent, confident answer grounded in no real source. Ask Nova Lite about a 35-day-old tent return and it will either admit it has no policy or invent a plausible 30- or 60-day rule. Both outcomes are the lesson.

Evidence vs action

The most important idea in the course

Retrieval gives the model evidence to read. A tool performs an action. Text that describes an action is neither.

ThingWhat it isCan change an order?
1InferenceThe model generating text from patternsNo, only describe one
2RetrievalRead-only lookup of stored documentsNo, evidence only
3Tool callThe agent invoking real code with argumentsOnly if the tool is built to
4Side effectThe world actually changed: a refund issuedYes, and needs authorization

“I have processed your refund” is unacceptable unless a tool returned success.

RAG: retrieval-augmented generation

How a knowledge base works

Store your documents, find the passages most relevant to each question (retrieval), and hand them to the model with the question (augmented generation). The answer is then grounded and can cite its source.

To find “relevant”, every chunk is turned into an embedding, a long list of numbers that captures meaning. The question is embedded the same way and the store returns the nearest chunks. That is why “free express shipping” finds a chunk that only says “standard” and “express”: retrieval matches meaning, not keywords.

Building the knowledge base

Harness vs Runtime

Module 3

A Harness is an agent you define by configuration. A Runtime is the secure compute it runs in. The harness is built on top of a runtime.

Analogy · the launch pad

The Runtime is the launch pad: power, isolation, a clean slate for every flight. The Harness is the flight plan you file: which rocket (model), which instructions (prompt), which payload bays (tools). Change the flight plan and the pad stays the same.

Sessions, versions, endpoints

How a harness changes safely
  • Session: one conversation, running in its own isolated micro-VM, kept alive for an idle timeout (15 minutes by default) then recycled. Isolation is why one user's session cannot reach another's data.
  • Version: every Save Harness creates an immutable version. Adding the gateway makes Version 2.
  • Endpoint: a named pointer to a version. DEFAULT follows the latest; point it at an earlier version to roll back.
Trap · testing in an old session

Tools are loaded when a session starts. After you add a gateway, fix a policy, or add a target, click the X next to Session ID (or reload) to begin a new session. An old session will keep showing the old behaviour.

Tidbit · session vs Memory

The agent remembering your first question is session context, lost when the session ends. The AgentCore Memory resource the harness created (semantic and summarisation strategies, 30-day event expiry) is what can persist across sessions.

Tools, MCP and the Gateway

Module 6

A tool needs three things: a schema the model can read, code that runs, and a permission boundary between them. AgentCore Gateway is a managed MCP server that supplies the boundary.

The Model Context Protocol is an open standard: a server advertises tools with schemas, and an agent calls them by name. You register targets on the gateway (a Lambda, a REST API, a knowledge base) and it publishes each one as an MCP tool named <target-name>___<tool-name> (three underscores), for example orbit-MY_ID-order-tool___lookup_order.

[
  {
    "name": "lookup_order",
    "description": "Read-only lookup of a fictional ORBIT training order by order_id. It never issues a refund.",
    "inputSchema": {
      "type": "object",
      "properties": {
        "order_id": { "type": "string", "description": "Training order ID, for example ORB-1001" }
      },
      "required": ["order_id"]
    }
  }
]
Tidbit · what your Lambda receives

The gateway passes the tool's input properties as the event (so event["order_id"]) and puts the tool name and gateway IDs in context.client_context.custom. The same code works from a manual Test and from the agent.

Why the description matters

The model chooses tools by reading their description. “Read-only … never issues a refund” is both a routing hint and a promise the code keeps. A vague description is the most common reason an agent never calls a tool that is perfectly wired.

Authentication vs authorization

Two different questions

Authentication asks who are you? Authorization asks what may you do?

A valid token proves an approved app is calling. It does not prove that app may touch this order or run this refund. And it never grants AWS permissions: the agent's calls to Bedrock or Secrets Manager still go through its execution role, enforced separately.

Authenticated is not authorized for every action.

OAuth 2.0 in two minutes

Client credentials grant

An app gets an access token from an authorization server and presents it to a resource server.

OAuth roleToday it is…
ClientYour Lambda test function: an app client ID and a client secret
Authorization serverYour Cognito user pool and its /oauth2/token endpoint
Resource serverA name you register in Cognito, orbit-MY_ID-api, that owns scopes
ScopeA permission string in the token: orbit-MY_ID-api/invoke
Tidbit · M2M vs human sign-in

The client credentials grant is for machine-to-machine calls: no human, just client ID and secret. A person would use the authorization code grant with PKCE (the flow you saw in Mission 02's hosted login). The flows differ; the token validation you configure today is the same for both.

Anatomy of a JWT

JSON Web Token

Three Base64URL strings separated by dots: header (which key and algorithm), payload (the claims), signature (proof Cognito issued it and nobody altered it).

header · kid, algpayload · claims (readable by anyone)signature · verified with JWKS

Anyone holding a token can decode its payload. Never paste tokens into chat, screenshots, logs or test events; the test client in this mission deliberately never returns or prints one.

Two boss challenges

Analysis only
B1

Audience confusion

Allowed audiences = client ID · Allowed clients empty

A perfectly good token is rejected, because the authorizer compares Allowed audiences with the aud claim, and Cognito access tokens carry client_id instead. The two checks validate different claims.

B2

Issuer mismatch

Token signed by Pool A · discovery URL points at Pool B

Rejected: the signature cannot be verified with Pool B's keys and iss does not match. Reason it through from the Inbound Auth panel; do not break your working authorizer to prove it.
