The three faults at a glance#

# Where it's planted What's wrong The clue that gives it away The fix
1 Bedrock AgentCore → Runtime → orbit_student07_am02_orchestrator → Environment variables GATEWAY_URL is an empty string Trace: gateway_configured: false, tools_discovered: 0; gateway pill amber 0 tools Set GATEWAY_URL to the Gateway's MCP endpoint URL (https://…gateway.bedrock-agentcore.us-west-2.amazonaws.com/mcp)
2 Gateways → orbit-student07-am02-gateway → Targets → logistics-target Its Lambda ARN points at orbit-student07-am02-inventory Shipment questions return stock counts; result_preview says "service": "inventory" and "warning": "inventory service received an unknown tool request 'track_shipment'…" Edit the target, keep its name and schema, change only the Lambda to …-logistics
3 Same Gateway, Targets list There are 3 targets, not 4: quality-target was never created Gateway pill 7 tools; quality question: I don't have a tool for that; S3 has 4 schema files but the gateway has 3 targets Add a Lambda target named exactly quality-target with the quality function, the quality_tools.json schema from S3 and the Gateway's IAM role
Important

Until fault 1 is fixed, faults 2 and 3 are invisible: with no Gateway address the agent never lists tools, so there's nothing to misroute and nothing to be missing. Replace student07 with your lab id throughout.

How the tool path is supposed to work#

Four facts explain every symptom:

  • The agent discovers tools at run time. discover_tools() in the orchestrator returns [] immediately when GATEWAY_URL is empty; it never even tries. That's what gateway_configured: false reports.
  • A target is a (name, Lambda ARN, schema, credentials) tuple. Tool names are targetName___toolName. The name decides what the agent sees; the ARN decides which function actually runs.
  • The Gateway tells the Lambda which tool was called through context.client_context.custom["bedrockAgentCoreToolName"]. Each OrbitOps tool Lambda reads that name and, if it isn't one of its own, returns its default report plus a warning field. That's why the misrouted call looks "successful".
  • Lambda targets use the Gateway's own IAM role to call the function. The role already allows lambda:InvokeFunction on all four of your tool Lambdas, so the missing target only needs the four parts above; no IAM work.

01Phase 110 minutesReading the evidence#

The first trace#

The trace under that reply:

JSON
{
  "token_source": "inbound",
  "gateway_configured": false,
  "tools_discovered": 0,
  "tools_called": [],
  "warnings": []
}

warnings is empty: nothing failed. The agent simply wasn't configured to look for tools. token_source: inbound confirms identity is fine (the Mission A chain is intact here), so don't touch Cognito or the authorizers.

The Gateway's targets#

Bedrock AgentCore → Gateways → orbit-student07-am02-gateway → Targets:

Target name Lambda it calls Verdict
inventory-target …:function:orbit-student07-am02-inventory ✔
supplier-target …:function:orbit-student07-am02-supplier ✔
logistics-target …:function:orbit-student07-am02-inventory ✘ name says logistics, ARN says inventory
(no fourth row) ✘ quality-target missing

Writing the name and ARN side by side, as the handout asks, is what makes fault 2 jump out: the last word of the ARN doesn't match the first word of the name.

The counts#

  • Lambda → Functions, filter student07-am02: 4 tool functions (-inventory, -supplier, -logistics, -quality) plus the chat handler.
  • S3 → the bucket from quality_schema_s3_uri → schemas/: 4 files: inventory_tools.json, supplier_tools.json, logistics_tools.json, quality_tools.json.
  • Gateway targets: 3.

Predict first the odd one out is the target count. Each schema file holds 2 or 3 tools (inventory 3, supplier 2, logistics 2, quality 2 = 9). With the quality target missing the agent can discover at most 7. Opening quality_tools.json shows the two tools you'll be adding: get_inspection_status and list_open_inspections.

02Phase 225 minutesThe fix, click by click#

Goal1Tell the agent where its tools are#

Expected: gateway_configured: true; gateway pill green with 7 tools (not 9 yet).

  1. Bedrock AgentCore → Gateways → orbit-student07-am02-gateway. On the overview, copy the Gateway URL (also called MCP endpoint). It looks like https://orbit-student07-am02-gateway-xxxxxxxxxx.gateway.bedrock-agentcore.us-west-2.amazonaws.com/mcp. It's also gateway_urls on your mission card. Not the ARN (arn:aws:bedrock-agentcore:…:gateway/…) and not the bare ID.
  2. Bedrock AgentCore → Runtime → orbit_student07_am02_orchestrator → Edit.
  3. Scroll to Environment variables. You'll see MODEL_ID, ORBIT_REGION, STUDENT_ID, GUARDRAIL_VERSION, CODE_SHA256 and an empty GATEWAY_URL. Paste the URL into GATEWAY_URL. Change nothing else.
  4. Save / Update runtime. Status goes READY → UPDATING → READY over roughly a minute while AgentCore creates version 2 with the new environment. The old version keeps answering (with 0 tools) until then.
  5. When it's READY, send Check our cargo stock levels again:

Trace: gateway_configured: true, tools_discovered: 7, warnings: []. Seven, not nine: faults 2 and 3 are now visible.

CloudShell alternative for Goal 1
Shell
RT=orbit_student07_am02_orchestrator-xxxxxxxxxx   # orchestrator_runtime_ids from your card
URL=https://orbit-student07-am02-gateway-xxxxxxxxxx.gateway.bedrock-agentcore.us-west-2.amazonaws.com/mcp

aws bedrock-agentcore-control get-agent-runtime --agent-runtime-id "$RT" > rt.json
jq --arg u "$URL" '{agentRuntimeId,agentRuntimeArtifact,roleArn,networkConfiguration,protocolConfiguration,
  authorizerConfiguration,requestHeaderConfiguration,
  environmentVariables:(.environmentVariables + {GATEWAY_URL:$u})}' rt.json > rt-update.json
aws bedrock-agentcore-control update-agent-runtime --cli-input-json file://rt-update.json --query '{status:status,version:agentRuntimeVersion}'
# poll until READY
aws bedrock-agentcore-control get-agent-runtime --agent-runtime-id "$RT" --query status
  • gateway_configured: true, 7 tools discovered.

Goal2Fix the droid that answers the wrong calls#

Expected: Where is shipment SHP-1001? returns a position, status and ETA, and result_preview says "service": "logistics".

First, see the fault in the trace. Ask Where is shipment SHP-1001?:

The pill says the right tool name was called. Expand the trace and read tools_called[0].result_preview:

JSON
"result_preview": "{\"service\": \"inventory\", \"warning\": \"inventory service received an unknown tool request 'track_shipment' - returning the stock summary instead\", \"requested_arguments\": {\"shipment_id\": \"SHP-1001\"}, \"total_skus\": 5, …"

That one line is the whole diagnosis: the Gateway forwarded track_shipment to a function that identifies itself as inventory. The name on the target is right; the ARN behind it is wrong.

Now fix it:

  1. Bedrock AgentCore → Gateways → orbit-student07-am02-gateway → Targets → logistics-target.
  2. Choose Edit. Do not delete and recreate: the name must stay logistics-target, and the schema is already correct.
  3. In the Lambda function field, replace the ARN with the logistics function. Pick orbit-student07-am02-logistics from the dropdown, or paste the logistics ARN from tool_function_arns on your card (arn:aws:lambda:us-west-2:111122223333:function:orbit-student07-am02-logistics).
  4. Leave Tool schema (S3 URI …/schemas/logistics_tools.json) and Credentials (Gateway IAM role) unchanged. Save.
  5. The target shows UPDATING for a few seconds, then READY. Ask again:

result_preview now starts {"service": "logistics", "shipment_id": "SHP-1001", … and there's no warning key.

Tip

The agent caches its tool list for 60 seconds, but a target edit doesn't change the list (same names, same schema), so there's nothing to wait for beyond the target's own READY.

CloudShell alternative for Goal 2
Shell
GW=orbit-student07-am02-gateway-xxxxxxxxxx    # gateway_ids from your card
LOGI=arn:aws:lambda:us-west-2:111122223333:function:orbit-student07-am02-logistics

TID=$(aws bedrock-agentcore-control list-gateway-targets --gateway-identifier "$GW" --query "items[?name=='logistics-target'].targetId" --output text)
aws bedrock-agentcore-control get-gateway-target --gateway-identifier "$GW" --target-id "$TID" > t.json
jq --arg a "$LOGI" '{gatewayIdentifier:.gatewayArn|split("/")[-1], targetId, name, description, credentialProviderConfigurations,
  targetConfiguration:(.targetConfiguration|.mcp.lambda.lambdaArn=$a)}' t.json > t-update.json
aws bedrock-agentcore-control update-gateway-target --cli-input-json file://t-update.json --query '{status:status,arn:targetConfiguration.mcp.lambda.lambdaArn}'
  • Shipment question returns shipment data; result_preview says "service": "logistics".

Goal3Add the missing quality tools#

Expected: gateway pill 9 tools; Show the status of cargo quality inspections calls a quality-target___… tool.

See the fault first:

The agent can only call what tools/list returned, and nothing in that list starts with quality-target___.

Now add it:

  1. Bedrock AgentCore → Gateways → orbit-student07-am02-gateway → Targets → Add target.
  2. Target name: quality-target (exactly: lowercase, hyphen, no spaces). The handout calls this the contract because the tool names quality-target___get_inspection_status and quality-target___list_open_inspections are derived from it.
  3. Target type: Lambda function.
  4. Lambda function: choose orbit-student07-am02-quality (or paste the quality ARN from your card).
  5. Tool schema: choose S3 (sometimes Define with S3 URI), and paste quality_schema_s3_uri from your card: s3://<code bucket>/schemas/quality_tools.json. Don't choose inline and retype the JSON; the file is already correct.
  6. Outbound authorization / Credentials: Gateway IAM role (the role the gateway already uses for the other three targets). No API key or OAuth provider.
  7. Add target / Create. It shows CREATING for 30–60 seconds, then READY. If it goes to FAILED, open it: the usual causes are a typo in the S3 URI or picking the wrong function.
  8. Wait up to a minute more (the agent refreshes its tool list every 60 seconds), then ask:
CloudShell alternative for Goal 3
Shell
GW=orbit-student07-am02-gateway-xxxxxxxxxx
QUAL=arn:aws:lambda:us-west-2:111122223333:function:orbit-student07-am02-quality
SCHEMA=s3://<code bucket>/schemas/quality_tools.json     # quality_schema_s3_uri from your card

aws bedrock-agentcore-control create-gateway-target \
  --gateway-identifier "$GW" \
  --name quality-target \
  --description "Quality inspections" \
  --credential-provider-configurations '[{"credentialProviderType":"GATEWAY_IAM_ROLE"}]' \
  --target-configuration "{\"mcp\":{\"lambda\":{\"lambdaArn\":\"$QUAL\",\"toolSchema\":{\"s3\":{\"uri\":\"$SCHEMA\"}}}}}" \
  --query '{name:name,status:status}'

Poll with aws bedrock-agentcore-control list-gateway-targets --gateway-identifier "$GW" --query 'items[].{name:name,status:status}' until all four are READY.

  • Gateway pill shows 9 tools; the quality question calls a quality-target___ tool.

Question tool result_preview begins What proves it's the right droid

Think about it: the answers#

  1. Why did the misrouted shipment call return stock data instead of an error? The inventory Lambda is written to be forgiving: for a tool name it doesn't own it returns its default summary and adds a warning. That's convenient for a demo and dangerous in production, because the model happily summarises whatever JSON comes back. A stricter tool would raise an exception (so the Gateway returns an MCP error and the agent says "that tool failed") or return {"error": "unsupported tool 'track_shipment' for service inventory"} with no data payload at all.
  2. How could the Gateway's tool list alone have told you a family was missing? Run tools/list (or look at the Targets tab and count): 3 targets, and none named quality-target. The names are the inventory of capabilities; you don't need to chat to audit them. The handout's "count three things" hint is exactly this.
  3. If someone edits a schema file in S3, does the Gateway notice? No. The Gateway reads the schema when the target is created or updated and stores it. Changing the object in S3 does nothing until you edit the target (even a no-op save) so it re-reads the URI, or you recreate the target.

Key takeaways#

  • No address, no tools. GATEWAY_URL is the single switch between "agent with tools" and "chatbot". gateway_configured in the trace reports that switch, nothing more.
  • Target name is the label; Lambda ARN is the wiring. Audit targets by putting name and ARN side by side.
  • Wrong wiring fails silently when tools are forgiving. result_preview and the tool's own service field are the truth; the pill only shows the name the agent asked for.
  • A target has four parts: name, function, schema (S3 URI or inline), credentials (Gateway IAM role for Lambda). Nothing else is needed because the Gateway role already has lambda:InvokeFunction on all four functions.
  • Runtime edits version; target edits don't. Wait for READY on whichever resource you changed, and give the agent's 60-second tool cache a moment after adding a target.
